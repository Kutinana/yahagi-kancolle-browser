# Yahagi v1.0.5 Beta 发布设计

## 目标

生成供测试群覆盖安装的 Android 预发布安装包。首个测试包版本为 `1.0.5-beta.1`，位于正式版 `1.0.4` 与 `1.0.5` 之间。后续根据反馈继续发布 `beta.2`、`beta.3` 等迭代，最终发布正式版 `1.0.5`。

升级安装必须保留 `1.0.4` 已下载的游戏资源缓存，不得要求测试用户重新下载。

## 版本策略

首个 Beta 包采用以下版本信息：

- `versionName`：`1.0.5-beta.1`
- `versionCode`：`6`
- 分发文件名：`Yahagi-v1.0.5-beta.1.apk`

后续每个 Beta 包都递增预发布序号和 `versionCode`。正式版使用 `versionName 1.0.5`，并使用高于所有已分发 Beta 包的 `versionCode`。

## 升级兼容约束

Beta 包必须继续使用：

- 应用包名 `app.yahagi.kancollebrowser`；
- `Yahagi Release` 正式签名证书；
- 现有应用数据目录和缓存路径 `files/game_resource_cache`。

不新增产品风味（Product Flavor），不使用独立 Beta 包名，也不要求卸载旧版本。Android 应将 Beta 包识别为 `1.0.4` 的原位升级，因此保留应用私有数据、登录状态、设置和游戏资源缓存。

如果目标设备安装的旧 APK 并非使用同一证书签名，Android 会拒绝覆盖安装；不得通过卸载旧版规避签名错误，因为卸载会删除应用私有缓存。

## 实现范围

本次只修改项目版本声明，不改变缓存格式、缓存索引、存储目录或应用标识。使用现有 release 签名配置构建通用 APK，并将成品复制到项目根目录，使用约定的分发文件名。

## 验收标准

1. 项目自动化测试和静态分析通过。
2. release APK 构建成功。
3. APK 清单显示包名为 `app.yahagi.kancollebrowser`、`versionName` 为 `1.0.5-beta.1`、`versionCode` 为 `6`。
4. 新 APK 与现有 `Yahagi-v1.0.4.apk` 的签名证书 SHA-256 摘要一致。
5. APK 可作为 `1.0.4` 的升级包安装，不需要卸载旧版。
6. 若有可用测试设备，执行覆盖安装，并核对安装前后的 `files/game_resource_cache` 文件数量与总大小没有减少；若无设备，则以包名、递增版本码、签名一致性和缓存路径未变作为静态升级兼容证据。

## 非目标

- 不制作可与正式版并存的独立 Beta 应用。
- 不迁移或重建游戏资源缓存。
- 不清理用户数据、WebView 数据或应用设置。
- 不把 Beta 包发布到正式更新渠道。
