# POI 引擎跨节点损管状态设计

## 背景与根因

默认 POI 预测引擎会在每个战斗节点创建一个新的
`PoiBattlePredictionEngine`。同一节点内，昼战、夜战和其他阶段通过不可变数据包历史
完整重放，因此同一件应急修理要员或应急修理女神不会重复触发。

进入下一个节点时，`BattleController` 会把预测引擎重置，并根据本地
`GameState` 重新建立舰队快照。游戏在出击途中不会用母港完整数据刷新装备槽，
本地快照仍会包含上一节点已经消耗的损管。新引擎因而可能把该损管再次视为可用，
形成跨节点错误复活。

POI 当前参考实现同样以节点为战斗模拟边界，没有维护出击级损管消费账本。
本次继续使用 POI 的阶段调度、目标路由、伤害、等级和 MVP 规则，但补充符合游戏
实际机制的出击级消费状态。

## 目标

- 同一次出击中，损管在一个节点消耗后，后续节点不得再次使用同一装备实例。
- 保持同一节点内现有的重放、损管顺序和多段攻击语义不变。
- 按舰娘实例 ID 和装备实例 ID 追踪，不按舰队位置追踪。
- 返回母港或开始全新出击时重置账本，`map/next` 时保留账本。
- 数据链不完整或状态无法核实时关闭式失败，把预测标记为未确认，不伪造确定结论。
- 只增强默认 POI 预测路径；Yahagi 加强引擎的算法和输入保持不变。
- 没有跨节点损管消费时，原有战斗预测结果逐字段保持一致。

## 非目标

- 不改变攻击阶段顺序、目标索引、七舰边界、NPC 友军、等级或 MVP 公式。
- 不重写现有单节点损管结算。
- 不修改服务器舰队和装备库存，不把预测消费写回 `GameState`。
- 不在磁盘持久化出击账本。应用中途启动且缺少前序节点时，采用未确认状态。
- 不把本次修复扩展到 Yahagi 加强引擎。

## 方案比较

### 方案 A：完全沿用 POI 的节点级状态

改动最少，但会保留已确认的跨节点重复使用问题，无法满足目标。

### 方案 B：按舰娘记录已消费的损管 Master ID

实现简单，也能通过 Master ID 多重集处理两个相同要员。但它无法直接证明具体消费
了哪个装备实例，状态校验能力较弱。

### 方案 C：控制器维护装备实例账本，并向 POI 引擎注入 Master ID 消费序列

这是选定方案。控制器能从 `GameState.equipmentForShip` 获得装备实例 ID、Master ID
及装备顺序；POI 引擎继续使用现有 `usedDamageControlItemIds` 计算剩余损管。
这样既能精确核对具体装备，又不需要扩大 `BattleShipSnapshot` 或预测引擎接口。

## 架构与职责

### 出击损管账本

新增一个独立、纯内存的 `SortieDamageControlLedger`，只负责记录和核对消费状态。
账本不依赖舰队位置，核心数据为：

- 舰娘实例 ID (`ownedShipId`)；
- 装备实例 ID (`instanceId`)；
- 装备 Master ID（要员 `42`、女神 `43`）；
- 消费顺序；
- 当前状态是否可信。

账本提供三个纯操作：

1. 根据舰娘 ID 返回已经消费的 Master ID 序列，用于建立新节点快照；
2. 根据预测输出和当前装备实例顺序同步完整消费结果；
3. 在前缀、实例或数据链无法核实时进入不可信状态。

“同步”采用整体核对，不采用每次回放就盲目追加。对同一预测结果重复同步，账本必须
保持不变。

### 控制器集成

`BattleController` 持有一个账本，职责边界如下：

- `map/start`：开始全新出击，清空旧账本并建立新账本；
- `map/next`：保留账本，只重置当前节点预测引擎；
- 昼战、夜战和战斗结果：保留账本；
- `api_port/port`、`api_start2/getData`：结束出击并清空账本；
- 演习：不读取、不写入出击账本；
- 未经过 `map/start` 或 `map/next` 就收到出击战斗包：视为中途接入，账本不可信。

控制器在创建 POI 引擎前，按舰娘 ID 把账本中的已消费 Master ID 序列写入新节点的
`BattleShipSnapshot.usedDamageControlItemIds`。创建 Yahagi 引擎时不执行注入。

POI 引擎完成一次预测后，控制器执行同步：

1. 按舰娘 ID 读取预测输出的完整消费序列；
2. 验证已有账本序列是输出序列的前缀；
3. 对每个新增 Master ID，按舰娘当前装备顺序寻找第一个尚未消费的匹配实例；
4. 找到后记录具体实例，找不到或顺序矛盾时将账本标记为不可信；
5. 再次处理同一完整结果时不得产生重复记录。

### 关闭式失败

出现以下情况时，不猜测损管状态：

- 战斗包存在解析问题；
- 发生损管消费但舰娘实例 ID 缺失；
- 预测消费序列与已有账本前缀不一致；
- 找不到对应的装备实例；
- 应用在出击途中接入，缺少前序节点。

账本进入不可信状态后，本次出击后续 POI 预测均标记为未确认。控制器不得把这种结果
当作权威 HP 写入全局舰队状态；界面可以保留带“未确认”标识的战斗预览。返回母港
或新的 `map/start` 会结束该不可信状态。

如果普通母港数据成功到达，游戏状态先由现有事件管线刷新，战斗控制器再销毁旧账本。
损管是否仍装备以服务器刷新后的舰娘装备槽为准，不需要用户手动刷新。

## 数据流示例

舰娘 `1001` 依次装备要员实例 `501` 和女神实例 `502`：

1. A 节点第一次致命伤，POI 输出消费序列 `[42]`；账本记录实例 `501`。
2. `map/next` 重置节点引擎，但账本保留。
3. B 节点初始快照注入 `[42]`；再次致命伤时只能选择 `43`。
4. POI 输出 `[42, 43]`；账本新增实例 `502`。
5. 同一输出因重放再次同步时不发生变化。
6. 返回母港后账本清空，服务器装备槽刷新为实际状态。

## 兼容性边界

- `BattlePredictionEngine` 接口保持不变。
- `PoiBattlePredictionEngine` 的阶段和伤害算法保持不变。
- `BattleShipSnapshot` 不增加装备实例字段，避免影响 UI、记录和另一套引擎。
- 官方 POI 单节点语料不包含跨节点上下文，结果应与修改前完全一致。
- 七舰、联合舰队和退避只改变舰娘所在位置，不改变 `ownedShipId`，因此不会串船。
- NPC 友军和敌舰没有玩家舰娘实例 ID，不进入账本。

## 测试策略

### 账本单元测试

- 要员、女神和 `[42, 43]` 按装备顺序映射到实例。
- 两个相同要员 `[42, 42]` 分别映射到两个实例。
- 同一完整结果重复同步保持幂等。
- 输出前缀矛盾、缺少舰娘 ID 或找不到实例时进入不可信状态。
- 舰队位置改变但舰娘 ID 不变时，消费状态仍属于原舰娘。

### 控制器跨节点测试

- A 节点消耗要员，B 节点再次致命时不能复用。
- A 节点消耗要员，B 节点使用女神。
- 七舰游击部队 0～6 号位分别携带或不携带损管，第 7 舰不串到敌舰。
- 联合舰队主力、随伴和退避后仍按舰娘 ID 继承。
- 昼战到夜战不重复消费；`map/next` 保留；母港和新 `map/start` 重置。
- 演习和 Yahagi 加强引擎不注入出击账本。
- 中途接入、非法目标和装备实例不匹配时标记未确认，且不发布预测 HP。

### 回归验证

- 修改前关键基线：POI 引擎与战斗控制器共 61 项测试通过。
- 运行全部战斗相关测试，包括两套引擎、友军、七舰、联合舰队、战斗记录和警告。
- 修正 POI 对照测试写死 `303`、官方仓库实际 `304` 的夹具数量门槛。
- 重新构建官方 POI oracle，并逐包比较 304 个文件、366 个战斗包的 HP、等级和 MVP。
- 运行完整 Flutter 测试和静态分析。
- 在最终合并到 `master` 后再次运行关键回归测试，且不覆盖 `master` 上用户已有改动。

## 成功标准

- 旧代码可稳定复现 A 节点损管在 B 节点被再次使用，新代码使该测试通过。
- 没有跨节点损管的场景，新旧 POI 输出逐字段一致。
- 跨节点消费按舰娘实例和装备实例精确继承，重复回放不重复记账。
- 不可信状态不会产生被当作权威值写回的预测 HP。
- 战斗专项、POI 官方语料、完整测试和静态分析均通过后才允许合并。
