# 装备开发工具设计

## 背景

Yahagi 工具箱当前包含「舰队导出」与尚未实现的「其他」模式。本次将「其他」替换为原生的「装备开发」功能，让用户在应用内完成以下两类查询：

- 给定秘书舰与油、弹、钢、铝配方，查看装备出货率与最低资源要求；
- 选择一个或多个目标装备，反推出可用配方、目标出货率和失败率。

功能行为参考 [SkywalkerJi/kc-development-tools](https://github.com/SkywalkerJi/kc-development-tools)。参考项目作者已向项目维护者确认可以使用相关实现与数据，但要求 Yahagi 不照抄其 UI。本项目继续采用 MIT 许可证；正式接入的数据文件必须在第三方数据说明中记录来源、固定提交和授权情况。

## 设计目标

- 在工具箱中提供完整的正向试算与反向配方查询。
- 全部计算在本地完成，首版不依赖网络。
- 复用 Yahagi 已有的游戏状态、装备图标、三语言框架和响应式布局。
- 使用独立的 Flutter UI，不复制参考网站的双栏表格布局与视觉样式。
- 将计算核心与 Flutter Widget 分离，确保算法可以独立测试。
- 建立可重复执行的数据转换与校验流程，不依赖参考项目未公开的测试向量生成工具。

## 非目标

- 首版不提供远程数据更新、自动定时同步或后台联网。
- 不执行游戏内开发操作，也不向游戏 WebView 注入配方。
- 不统计用户实际开发历史，不根据个人历史估算概率。
- 不新增英文界面；语言范围与 Yahagi 当前支持的简体中文、繁体中文和日文一致。
- 不复制参考网站的 Vue 组件、CSS、页面结构或交互排布。

## 工具箱入口

`ToolboxMode` 从「舰队导出 / 其他」调整为「舰队导出 / 装备开发」。现有顶部胶囊标签保持两项，不扩展为 3 项。

选择「装备开发」后，`ToolboxPage` 展示新的 `EquipmentDevelopmentPage`。页面接收最新 `GameState`，以便识别当前第一舰队旗舰并使用运行时 Master 名称；计算数据由独立的数据仓库提供。

## 页面布局

页面采用已确认的 A「指挥仪表盘」方案，沿用 Yahagi 的深海蓝背景、旧金色强调色、圆角面板和紧凑信息密度。

### 顶部开发条件

顶部使用一张横向条件卡，包含：

- 秘书舰选择器；
- 「使用当前旗舰」快捷按钮；
- 油、弹、钢、铝 4 个数字输入控件；
- 当前判定的开发池类型提示。

宽屏下 4 项资源并排显示；窄屏下允许换成 2 × 2 排列。资源值只接受整数，并限制在 10–300。输入尚未形成合法整数时保留上一次有效计算结果；失焦后将越界值夹到合法范围。

### 主体区域

宽屏采用左右双栏：

- 左栏显示当前配方的可能产出；
- 右栏显示目标装备与推荐配方。

窄屏改为上下排列，顶部开发条件始终位于两块结果之前。页面使用单一主纵向滚动区域，不在左右面板中嵌套不可控的长滚动区域；推荐配方表允许局部横向滚动。

### 当前配方产出

左栏按以下顺序分组：

1. 目标装备；
2. 其他装备；
3. 资源不足；
4. 全部被替换。

每个分组显示合计出货率。装备行显示装备类型图标、名称、逐池出货率明细和最低资源要求。总出货率为 0、但存在正负池抵消的装备归入「全部被替换」，仍显示原始叠加明细，例如 `2%-2%`。

### 目标装备选择

右栏平时只显示已选择的装备胶囊与「添加」按钮，不常驻展示全部可开发装备。

点击「添加」后，从底部打开装备选择面板：

- 面板顶部显示标题和圆形搜索按钮；
- 不显示常驻长条搜索框；
- 搜索按钮按下后，使用项目已有的独立输入弹窗显示搜索输入框；
- 输入框自动获得焦点，并即时显示名称匹配结果；
- 面板提供装备类型筛选胶囊；
- 装备按类型、图标类型和 ID 稳定排序；
- 已选择装备保持高亮，再次点击可取消；
- 当前目标组合下不可能共同开发的装备置灰，但已经选中的装备仍允许取消。

选择或取消装备后立即刷新可用配方。关闭搜索弹窗后返回原来的底部面板，不丢失分类、选择和滚动位置。

### 推荐配方

未选择目标装备时显示引导空状态。选择目标后，推荐配方至少显示：

- 油、弹、钢、铝；
- 开发池类型；
- 总资源；
- 目标装备合计出货率；
- 失败率。

默认排序遵循参考功能的既有语义：先按目标出货率降序，再按总资源升序，最后按失败率降序。用户可以点击表头切换排序字段和方向。

点击某条配方会：

1. 将 4 项资源回填到顶部输入；
2. 选择该配方对应的秘书舰池；
3. 立即刷新左侧当前配方产出；
4. 高亮当前应用的配方行。

重复点击已经应用的配方不覆盖用户之后手动修改的输入。

## 秘书舰行为

首次进入页面时：

- 若母港状态中存在第一舰队旗舰，则选择该舰对应的最窄开发池；
- 若当前旗舰无法匹配或母港数据尚未准备好，则选择数据集中的默认可选池。

用户手动选择秘书舰或开发池后，本次页面生命周期内保持手动选择。游戏状态刷新、换编成或旗舰变化不会突然覆盖查询条件。「使用当前旗舰」按钮用于用户主动重新同步。

秘书舰选择器支持按舰名搜索，也允许直接选择开发池。运行时 Master 数据存在时优先使用其舰名；否则回退到内置快照名称。

## 数据设计

### 内置快照

新增 `assets/data/development/development_snapshot.json`。快照是首版计算的唯一权威数据，至少包含：

- `schema_version`；
- `data_version`；
- 参考仓库 URL 与固定提交号；
- 生成时间与源文件 SHA-256；
- 已解析的开发池；
- 可开发装备目录；
- 秘书舰目录和舰娘到最窄开发池的映射。

开发池记录包含：

- 稳定池标识与三语言显示键；
- 简体中文、繁体中文和日文显示名称；
- 池类型 ID；
- 已解析的适用舰娘 Master ID 集合；
- 可选的最低资源门槛；
- 装备 ID 到出货率增量的映射。

装备记录包含：

- 装备 Master ID；
- 内置日文名称；
- 装备类型与图标类型；
- 4 项废弃资源值，用于计算最低开发资源。

生成后的快照直接保存已解析舰娘 ID，运行时不再重复展开「舰种 / 舰级 / 舰名 / 排除舰」条件。这可以减少页面初始化复杂度，并让数据校验集中在构建阶段。

### 数据同步工具

新增 `tool/development_data/`，提供可重复执行的 Dart 同步工具。工具接收固定版本的参考项目目录，读取 `DevelopmentPool.json`、`ctype.json` 和 `start2.json`，完成以下步骤：

1. 校验源文件结构和字段范围；
2. 展开开发池的舰种、舰级、舰名与排除条件；
3. 校验所有出货率装备 ID 均存在；
4. 生成紧凑的装备和秘书舰目录；
5. 输出稳定排序、格式化的快照；
6. 记录源提交、文件哈希、记录数量和生成时间；
7. 对生成结果重新解析并执行交叉引用校验。

同步工具不得依赖参考仓库未公开的向量生成程序。快照更新必须产生可读的 Git diff，并在提交前运行算法回归测试。

### 名称覆盖

算法只使用稳定 ID，不依赖显示名称。页面的名称优先级如下：

1. 当前或缓存 `GameState` 中的游戏 Master 名称；
2. 内置快照的日文名称；
3. `#<ID>` 兜底文本。

通用 UI 文案、池类型和筛选条件通过 Yahagi ARB 文件本地化。46 个开发池名称是授权参考数据的一部分，由同步工具写入快照的三语言名称表，并按当前 Locale 读取；这样无需为数据记录生成静态 Dart getter。第三方翻译数据若来自参考项目或 KC3Kai，必须在 `THIRD_PARTY_DATA.md` 与 `THIRD_PARTY_NOTICES` 中保留其来源和许可说明。

## 计算核心

新增 `lib/src/development/` 模块，并按职责拆分：

- `development_dataset.dart`：快照模型、解析与完整性校验；
- `development_repository.dart`：加载内置数据并缓存解析结果；
- `development_pool_matcher.dart`：开发池匹配与出货率叠加；
- `development_recipe_calculator.dart`：资源池判定、反推配方和配方评估；
- `development_projection.dart`：装备分组、排序和页面投影；
- `equipment_development_controller.dart`：页面状态与用户操作；
- `equipment_development_page.dart`：响应式页面与弹窗。

纯计算文件不得依赖 Flutter Widget、`BuildContext` 或本地化对象。

### 开发池判定

资源顺序固定为油、弹、钢、铝：

- 铝严格大于油、弹、钢时使用铝池；
- 否则弹严格大于油、钢时使用弹池；
- 其余情况使用油钢池。

并列值必须遵循上述短路顺序，不能改成简单取最大值索引。

### 正向计算

给定基础秘书舰池、资源和池类型后：

1. 找出舰娘集合包含基础池的兼容池；
2. 应用额外最低资源条件；
3. 按池宽度与出货率条目数稳定排序；
4. 逐池合并装备出货率增量；
5. 按装备最低资源和目标选择状态完成分组。

负出货率条目必须保留，不能提前夹到 0，否则会丢失装备被替换的语义。

### 反向计算

给定目标装备集合后，遍历可选秘书舰池与 3 类资源池：

1. 合并对应兼容池的出货率；
2. 过滤不能同时产出全部目标装备的组合；
3. 根据目标装备最低资源生成最小候选配方；
4. 调整资源大小关系，使配方落入目标资源池；
5. 计算目标出货率、其他装备出货率、失败率和总资源；
6. 对结果稳定排序。

九六式陆攻的特殊最低配方规则必须作为明确的领域规则单独测试，不散落在 UI 或通用循环中。

## 状态管理

`EquipmentDevelopmentController` 负责：

- 当前秘书舰池；
- 是否已由用户手动覆盖当前旗舰；
- 4 项资源的编辑值与最后有效值；
- 目标装备集合；
- 当前配方产出；
- 可用反推配方；
- 装备类型和名称筛选；
- 配方排序字段、方向和当前应用项。

数据集在应用启动阶段或首次打开页面时加载一次。游戏状态变化只更新名称覆盖与「当前旗舰」候选，不重建开发池索引。计算量较小，合法资源输入和目标变化可以同步重算；Widget 构建过程中不得重复解析 JSON 或重建全量索引。

首版只保存页面生命周期内的状态，不把资源配方、目标装备或搜索词写入持久化存储。

## 错误与边界处理

- 内置快照加载失败或校验失败：不展示可能错误的计算结果，显示明确的数据不可用状态与重试按钮。
- 当前游戏 Master 尚未准备好：继续使用内置名称和秘书舰目录，功能仍可离线使用。
- 某个运行时名称缺失：回退快照名称，再回退到 ID。
- 当前旗舰不在秘书舰目录：保持现有池并显示无法匹配提示。
- 未选择目标装备：推荐配方区域显示引导空状态。
- 目标组合没有共同配方：保留选择，显示「没有可同时开发这些装备的配方」，允许逐项取消。
- 输入为空、含非整数或处于输入法组合阶段：不提交本轮计算。
- 配方结果为空或数据引用缺失：不得抛出到 Widget 树，记录调试信息并显示局部空状态。
- 页面在窄屏、横屏和文字放大场景下不得产生 RenderFlex 溢出。

## 授权与数据说明

实现前需要把参考作者的授权确认留存在项目维护记录中。仓库内至少补充以下信息：

- 参考项目名称与 URL；
- 本次使用的固定提交；
- 使用范围：开发池数据、行为参考和必要的名称数据；
- 作者提出的限制：不得照抄原项目 UI；
- Yahagi 使用独立 Dart 实现和独立 Flutter UI；
- 数据可能随游戏更新而过时，实际结果以游戏为准。

若授权文本要求额外署名、许可证文件或分发条件，应以授权文本为准更新说明。本设计不把本次使用确认扩大解释为未明确授予的商标、图片或游戏素材授权。

## 测试要求

### 数据测试

- 快照 schema、版本和元数据完整；
- 开发池、装备与秘书舰引用不存在悬空 ID；
- 资源数组长度固定为 4，值域合法；
- 出货率允许负数，但拒绝非有限数；
- 可选池名称与 ID 组合唯一；
- 同一源数据重复生成得到除生成时间外完全一致的结果。

### 算法单元测试

- 3 类资源池的严格大于与并列边界；
- 兼容池的舰娘超集判断；
- 最低资源池的过滤；
- 正负出货率叠加和全部被替换分组；
- 多目标装备的共同池过滤；
- 油钢池生成 1 个或 2 个候选配方的边界；
- 九六式陆攻特殊配方；
- 目标出货率、失败率、总资源和默认排序；
- 当前目标组合下装备启用集合。

从参考实现选取一组覆盖边界的固定输入输出作为数值回归夹具，但夹具由本项目同步工具生成并记录来源版本，不直接依赖参考仓库的测试运行环境。

### Widget 测试

- 工具箱「其他」标签替换为「装备开发」；
- 有母港数据时首次选择当前第一舰队旗舰，无母港数据时使用默认池；
- 手动选择后游戏状态刷新不覆盖，点击「使用当前旗舰」才同步；
- 资源输入校验、即时重算与越界归一化；
- 宽屏双栏和窄屏上下布局；
- 正向结果 4 个分组及明细展示；
- 点击「添加」打开底部装备面板；
- 面板不显示常驻长条搜索框；
- 点击圆形搜索按钮后弹出输入框，确认、取消、清空和搜索结果行为正确；
- 多目标选择、不可用装备置灰和无共同配方状态；
- 点击推荐配方回填资源、切换池并高亮结果；
- 简体中文、繁体中文和日文关键文案存在；
- 窄屏与大字体下无布局溢出。

## 验收标准

- 正向试算和反向配方两条主流程均可离线使用。
- 选定回归夹具的数值结果与授权参考数据一致。
- UI 符合确认的 A「指挥仪表盘」布局，目标装备搜索采用按钮加弹出输入框，不复刻参考网站页面。
- 当前旗舰快捷识别、手动池选择和配方回填行为稳定。
- 数据转换可重复执行，来源、固定提交、哈希与授权说明完整。
- 相关单元测试、Widget 测试和静态分析全部通过。
