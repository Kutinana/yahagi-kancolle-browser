# KCWiki 数据贡献上报设计

## 目标

在 Yahagi 中增加一个完全可选的 KCWiki 数据贡献功能。用户在“设置 → 数据”中主动开启后，应用才收集并上传 KCWiki 所需的带路、任务、战斗、友军、陆航和改修数据；默认关闭时不产生 KCWiki 专属处理、缓存或网络请求。

本功能只实现 KCWiki `report2` 数据，不实现 POI 的建造、开发和掉落上报。

## 产品边界

- 总开关默认关闭，并使用本地设置持久化。
- 设置入口位于 `DataSettingsPage` 的数据设置页面。
- 开启前明确告知上传的数据类别，以及可能产生少量流量和电量消耗。
- 关闭后拒绝新上报、清空尚未发送的内存任务，并关闭 KCWiki 专用 HTTP 客户端。
- 本功能是辅助贡献功能。解析、组包、排队、超时、服务端错误以及网络异常都不得阻塞游戏事件管线、游戏画面或 Yahagi 原有功能。
- 不创建 Android 常驻后台服务；“后台上传”只表示应用运行期间异步执行。

## 数据范围

| 上报模块 | KCWiki 路径 | 数据来源 |
|---|---|---|
| `next_way_v2` | `/api/report/next_way_v2` | 地图信息、出击开始、逐节点前进、舰队/装备快照、联合舰队和退避状态 |
| `quest` | `/api/report/quest` | 完成任务请求以及完成前后的任务列表差异 |
| `battle` | `/api/report/battle` | 同一节点的昼战、夜战、战果、舰队战前/战后状态和陆航信息 |
| `friendly_info` | `/api/report/friendly_info` | 友军设置、夜战友军数据、地图和敌舰上下文 |
| `air_base_attack` | `/api/report/air_base_attack` | 地图前进响应中的基地航空队空袭数据 |
| `remodel` | `/api/report/remodel` | 改修列表、改修详情和改修助手舰信息 |

客户端不得把任意捕获内容直接转发给服务器。每个模块必须有独立的构造器和明确字段映射。`battle` 中为兼容旧插件而保存的战斗响应包也只能来自已列入战斗路径白名单的游戏响应。

## 架构

### 设置与生命周期

新增 `KcwikiReportSettingsStore` 和 `KcwikiReportController`：

- Store 使用 `SharedPreferences` 保存总开关，缺失值按 `false` 处理。
- Controller 负责开关状态、启动/停止 reporter 和向设置页面通知状态变化。
- 关闭操作先切断事件入口，再清空 reporter 会话和待发送队列，最后关闭专用 HTTP client。
- 重新开启时创建全新的会话和 HTTP client，不复用关闭前的数据。

### 事件收集

新增 `KcwikiReportConsumer`，实现现有 `GameApiEventConsumer` 接口并注册到 `GameApiEventPipeline`。Consumer 只做三件事：

1. 检查总开关和受支持路径。
2. 将事件交给独立、串行的 KCWiki 会话状态机。
3. 捕获所有内部异常并转为不含正文的状态统计。

Consumer 的 `accept` 不等待网络，不把上传 Future 返回给游戏事件管线。组包和上传使用独立队列；即使 KCWiki 服务不可用，原有的 `GameStateController`、`BattleController` 和其他 consumer 仍按原流程执行。

KCWiki 独占路径只在开关开启时加入捕获策略。原本已被 Yahagi 使用的共享路径仍正常捕获，但开关关闭时不会交给 KCWiki consumer。

### 会话状态机

按旧 `kcwiki-report` 的跨事件规则维护仅存在于内存的状态：

- 带路：在出击开始时记录舰队和地图状态，每次 `start`/`next` 生成节点记录。
- 任务：记录 `clearitemget` 的任务 ID，并在下一次 `questlist` 到达时比较前后列表。
- 战斗：按地图节点聚合战斗阶段，在战果、进入下一节点或回港时封装完整记录。
- 友军：在夜战发现友军时暂存，在所需上下文完整后生成记录。
- 陆航：仅当地图响应包含对应字段时生成记录。
- 改修：把改修列表、详情和助手舰上下文组合成记录。

会话状态不写入磁盘；应用终止、用户关闭开关或捕获会话重置时全部丢弃。

### 隐私边界

- 沿用捕获层对 `api_token` 和 `api_starttime` 的递归移除。
- 不上传 Cookie、HTTP Header、网页地址、诊断日志或 Yahagi 本地设置。
- 不在日志、错误信息或界面状态中保存完整上报正文。
- 每类序列化器使用字段白名单；游戏接口未来新增的字段不会自动进入上报内容。
- 任何希望增加的 `reporter`、`reporterVersion`、`eventId` 和 `reportedAt` 字段，都必须先得到 KCWiki 服务端确认，不能自行向生产接口增加字段。

## 上传策略

- 客户端只调用 KCWiki HTTP 接收服务，不直接连接 MongoDB。
- 旧插件的兼容路径为 `report2.kcwiki.org:17027/api/report/*`。
- `friendly_info`、`battle`、`remodel` 使用 JSON；`air_base_attack`、`next_way_v2`、`quest` 使用表单编码，最终以 KCWiki 确认的接口契约为准。
- 使用 KCWiki 专用的单并发队列，避免瞬时并发请求。
- 首版队列上限为 16 条或 4 MiB，以先达到者为准；超过上限拒绝新任务并增加本地丢弃计数。
- 单条编码后正文上限为 2 MiB；超限记录不发送，也不截断。
- 单次请求超时为 8 秒。
- 在服务端没有幂等键之前，超时和结果不明确的请求不自动重试，避免重复落库。
- 仅 HTTP 2xx 视为“服务器已接受”；真正落库成功仍需服务端响应约定或 MongoDB 查询确认。

旧地址目前为明文 HTTP，且探测曾超时。生产联调和发布前，KCWiki 必须确认可用接收地址、请求编码、成功响应语义及是否提供 HTTPS。若只能使用明文 HTTP，设置页必须明确提示传输未加密，且发布决定需要再次审查。

## 状态与界面

数据设置页面增加“向 KCWiki 贡献数据”区域：

- 一个默认关闭的总开关。
- 描述六类上传数据，不使用“匿名”措辞，除非服务端确认实际匿名化规则。
- 展示最近一次传输结果的轻量状态：模块、成功/失败、时间和 HTTP 状态码。
- 不展示或保存请求正文。
- 关闭开关时立即更新界面；后台清理失败也不能阻止开关关闭。

## 测试与验收

### 自动化测试

1. Store 测试：缺失设置默认关闭，保存后能够恢复。
2. Controller 测试：开启、关闭、重复切换及关闭清队列行为。
3. 路径测试：关闭时不接受 KCWiki 独占路径；开启时只接受明确白名单。
4. 构造器契约测试：使用固定 `/kcsapi/` fixture 验证六类请求的字段、类型和编码。
5. 隐私测试：递归检查请求中不存在 `api_token`、`api_starttime`、Cookie 和 Header。
6. 上传器测试：本地 fake client 验证 URL、Content-Type、超时、2xx/非 2xx、正文上限和队列上限。
7. 隔离测试：上传器抛异常或永久等待时，其他 `GameApiEventConsumer` 仍能处理后续事件。
8. UI 测试：开关位于数据设置页、默认关闭、用户切换后持久化。

### 服务端联调

优先使用 KCWiki 提供的测试环境。若服务端允许并保存唯一 `eventId`，每个模块上传一条获准的真实游戏记录，再按 `eventId` 查询对应集合。若旧服务不支持唯一标识，则由 KCWiki 开发者提供可验证的响应字段或约定可查询的测试版本标识。

生产库不得通过 MongoDB 客户端手工插入测试记录。MongoDB 连接只用于只读核对由 HTTP 接收服务产生的记录。

### 性能验收

- 开关关闭时，KCWiki consumer 产生零上传请求，KCWiki 独占路径不进入专属处理。
- 开关开启但 KCWiki 服务不可用时，游戏 API 管线和界面仍可持续工作。
- 对真实单舰队、联合舰队和陆航战斗样本记录组包耗时、正文大小、队列峰值和请求耗时。
- 连续出击压力测试中不得出现游戏事件积压由 KCWiki 队列反向传播导致的增长。

## 发布门槛

以下条件全部满足后才能默认编入正式版本；总开关仍保持默认关闭：

1. KCWiki 开发者确认当前接收地址和六类请求契约。
2. 明确 HTTP 成功响应代表的语义。
3. 完成六类自动化契约测试和异常隔离测试。
4. 至少一台真机完成真实出击性能测试。
5. 通过 HTTP 上报并在对应 MongoDB 集合中只读确认落库。
6. 完成设置页数据说明和隐私审查。
