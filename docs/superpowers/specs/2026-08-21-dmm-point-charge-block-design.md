# DMM PT 充值阻断与既有余额结算设计

## 背景

舰 C 道具商店会在 DMM 游戏页面的顶层打开购买确认弹窗。应用需要允许玩家使用账号已有的 DMM PT 完成道具结算，但不应允许玩家从应用内进入 DMM 充值或储值页面。

充值按钮必须保持可见。玩家点击后，当前购买确认页保持原状，不跳转、不刷新，也不进入持续加载状态。

## 目标

- 允许 DMM 游戏内商品查询、购买确认和使用既有 PT 结算。
- 保留「ポイントをチャージする」按钮的原始外观。
- 点击充值按钮时静默停留在当前页面。
- 阻止通过脚本、链接或页面结构变化进入 DMM 充值地址。
- 不影响「返回游戏」、余额刷新、优惠券和已有 PT 购买操作。

## 非目标

- 不修改 DMM 账号余额。
- 不代替 DMM 实现购买或支付流程。
- 不隐藏、重命名或重新设计 DMM 收银台控件。
- 不开放第三方支付、信用卡、PayPay 或其他充值渠道。

## 设计

### 页面交互层

游戏页面呈现脚本在捕获阶段监听点击事件。命中 DMM 充值控件时调用 `preventDefault()` 和 `stopImmediatePropagation()`，使按钮成为无操作控件。

充值控件优先使用现场页面已有的稳定语义属性识别：

```text
[data-gtm-action-detail="link_charge-points"]
```

脚本不依赖按钮的日文文本或构建时生成的 CSS 类名。监听器随游戏页面呈现脚本安装，并在脚本重复执行时复用同一个处理器，避免重复绑定。

### 导航策略层

导航策略增加独立的 DMM 充值地址判定。即使页面脚本未能拦截点击，只要目标属于充值流程，WebView 仍静默阻止导航。

现场按钮实际调用以下新窗口地址：

```text
https://point.dmm.com/choice/pay?basket_service_type=freegame&...
```

该规则阻断 `point.dmm.com` 和 `point.dmm.co.jp` 整个主机，不依赖具体路径或查询参数。主机名必须通过 URI 解析后精确比较，不得使用字符串包含关系匹配完整 URL，也不得把普通 DMM 商品结算地址一并阻断。

普通结算接口与页面继续放行，包括当前使用的 DMM 游戏购买确认链路。非充值导航沿用现有安全策略。

### 用户反馈

按照已确认的交互，点击充值按钮不显示提示、不弹出错误，也不改变按钮外观。页面保持在购买确认状态，玩家可以返回游戏或在余额足够时继续购买。

## 数据流

1. 玩家在舰 C 道具商店点击使用 PT 购买。
2. DMM 购买确认弹窗显示，应用解除游戏 iframe 的全屏锁定。
3. 若已有 PT 足够，玩家点击 DMM 结算按钮，购买流程正常继续。
4. 若玩家点击充值按钮，页面捕获层立即吞掉事件。
5. 若充值动作仍产生导航，导航策略再次识别并静默阻止。
6. 当前购买确认页保持可交互，不出现加载卡死。

## 测试

- 页面脚本包含基于 `data-gtm-action-detail` 的充值控件识别。
- 充值点击处理器同时阻止默认行为和后续事件传播。
- 重复同步呈现不会重复安装处理器。
- 导航策略允许 DMM 游戏商品购买确认与结算地址。
- 导航策略拒绝 `point.dmm.com`、`point.dmm.co.jp` 及其路径、查询参数变体。
- 相似域名、用户信息伪装、HTTP 地址和非充值 DMM 页面覆盖边界测试。
- 现有游戏导航、登录和购买弹窗呈现测试继续通过。

## 验收标准

- 充值按钮保持可见。
- 点击充值按钮后 URL、页面内容和加载状态均不变化。
- 已有 PT 足够时可完成游戏内道具结算。
- 直接或间接发起充值导航均被静默阻止。
- 返回游戏和余额刷新仍可使用。
