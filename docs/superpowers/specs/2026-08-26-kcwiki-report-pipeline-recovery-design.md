# KCWiki 上报管线恢复设计

## 背景

KCWiki 数据贡献开关已能将带路与战斗记录发送到 `report2.kcwiki.org:17027`。云端只读核验确认，`version: "yahagi-1"` 已写入 4 条带路记录和 4 条战斗记录，共 8 条。

当前实现仍存在两个可靠性问题：

- 切换 KCWiki 开关会重新配置捕获脚本并刷新游戏页面。
- 大型游戏响应通过后台 Isolate 解析时可能长期不返回，导致全局事件队列发生队首阻塞（Head-of-line Blocking）。诊断记录曾显示待处理事件从 4 条增长到 14 条，后续 KCWiki 事件无法进入上传器。

KCWiki 上报属于可选贡献功能。无论其开关、网络、服务器还是数据解析发生何种异常，都不得阻塞游戏页面和现有核心功能。

## 目标

- 切换 KCWiki 开关不刷新游戏页面。
- 开关关闭时不生成、不缓存、不上传 KCWiki 报告。
- 开关开启时继续使用现有 6 个上报模块和 `yahagi-1` 版本标识。
- 大型响应解析不能无限阻塞后续事件。
- 解析超时后保留数据，通过同步兜底完成解析，不静默丢包。
- 设置页展示等待、解析恢复、上传成功和上传失败等真实状态。
- KCWiki 相关异常不得向游戏事件管线反向传播。

## 非目标

- 不新增 POI 上报。
- 不改变 KCWiki 服务器地址、接口路径或既有字段结构。
- 不重构全部游戏状态消费者。
- 不在设置页增加手动测试上传按钮。
- 不发送 Cookie、登录令牌、请求头或其他身份凭据。

## 方案

### 1. KCWiki 开关与捕获脚本解耦

游戏 WebView 始终安装包含 KCWiki 所需路径的稳定捕获脚本。KCWiki 开关只控制 `KcwikiReportConsumer` 与 `KcwikiReportDispatcher`：

- 开启时，消费者接收支持的事件并生成报告。
- 关闭时，消费者的 `supportsPath` 返回 `false`，上传队列停止并清空未发送报告。

`GameWebView` 与 `NativeActivityGameSurface` 不再监听 KCWiki 开关并调用 `reload()`。捕获脚本内容不随开关变化，因此打开或关闭开关不会重新加载游戏。

关闭状态下，额外路径只经过桥接层。由于没有消费者声明支持，事件管线不解码、不保存也不上传这些事件。

### 2. 后台解析超时与同步兜底

`GameApiEventPipeline` 保持事件顺序。需要后台解析的大型响应采用两阶段策略：

1. 首先在后台 Isolate 中解析，并设置明确的超时时间。
2. 超时后放弃等待该后台结果，在主 Isolate 中同步解析同一响应。
3. 同步解析成功后，按原顺序分发给全部消费者。
4. 同步解析也失败时，沿用现有无解码事件分发路径，让各消费者执行既有错误隔离逻辑。

后台超时只触发恢复，不视为丢包。兜底解析可能造成一次短暂卡顿，但不会让事件队列永久停滞，也不会破坏事件顺序。

超时时间作为 `GameApiEventPipeline` 的可注入构造参数。生产环境默认值为 5 秒，测试使用更短的确定值稳定复现。

### 3. 可观测状态

管线记录当前处理路径、队列深度和后台解析恢复次数。诊断事件不得包含响应正文、请求参数或用户舰队数据。

KCWiki 设置状态增加以下语义：

- 等待数据：开关已开启，但尚未生成任何报告。
- 处理中：已捕获可上报事件，正在生成或发送报告。
- 上传成功：显示最近模块、时间和累计成功数。
- 上传失败：显示最近模块、时间、HTTP 状态或本地失败类别。
- 解析已恢复：发生后台解析超时，但同步兜底成功；该状态不计为上传成功。

累计成功数应与每个收到 2xx 响应的报告一一对应。应用重启后保留最近状态和累计计数，避免成功记录恢复成“等待数据”。

### 4. 错误隔离

- KCWiki 收集器异常只增加丢弃计数并更新状态，不中断游戏状态消费者。
- HTTP 超时、网络错误和非 2xx 响应不重试当前报告，避免后台持续占用资源。
- 关闭开关立即停止后续报告，并使正在执行的结果失效；不得关闭游戏捕获管线。
- 应用销毁时关闭 HTTP Client 和上传队列，不保留后台任务。

## 数据流

```text
游戏请求
  -> 稳定捕获脚本（不随 KCWiki 开关变化）
  -> GameApiEventPipeline
       -> 小响应：同步解析
       -> 大响应：后台解析 -> 超时则同步兜底
  -> 核心游戏消费者
  -> KCWiki 消费者（仅开关开启时）
  -> report2 HTTP 接口
  -> KCWiki MongoDB
```

## 测试设计

### 自动化测试

- 开关切换不调用 WebView 或原生活动的 `reload()`。
- 关闭状态下 KCWiki 消费者不接收事件、不生成报告。
- 后台解析按预期超时时，测试先失败，再验证同步兜底成功。
- 超时兜底后，后续事件仍按序分发，待处理计数最终回到 `0`。
- 后台与同步解析均失败时，事件管线继续处理下一事件。
- KCWiki 状态正确区分等待、处理中、成功、失败和解析恢复。
- 累计成功数与 2xx 响应数量一致，并能跨重启恢复。
- 既有收集器、传输层、调度器和设置页测试全部通过。

### 真机测试

1. 保持游戏在母港，连续切换 KCWiki 开关，确认页面不刷新。
2. 开启 KCWiki 后进入普通海域，完成至少 4 个节点和 4 场战斗。
3. 返回母港，确认设置页显示 8 条上传成功，事件队列回到 `0`。
4. 使用只读 MongoDB 查询：
   - `nextwayv2records`：`{"version":"yahagi-1"}`。
   - `battlerecords`：`{"data.version":"yahagi-1"}`。
5. 对比操作前后的 `_id` 或记录数量，确认新增记录来自本次真机测试。
6. 断开网络后再次出击，确认游戏正常运行且设置页明确显示上传失败。

## 验收标准

- KCWiki 开关切换 10 次，游戏页面 0 次刷新。
- 最后一个游戏 API 事件进入管线后 15 秒内，事件队列回到 `0`；HTTP 上传队列单独计算，不阻塞该指标。
- 后台解析超时不会丢弃响应，也不会阻塞下一事件。
- 关闭 KCWiki 后不产生新上报请求。
- 服务器故障不影响游戏、战斗记录、任务和其他现有功能。
- 全量 Flutter 测试通过，Android Release APK 构建成功。
- 真机上传数量与 MongoDB 中新增的 `yahagi-1` 记录数量一致。

## 已有云端基线

2026-08-26 的只读核验结果如下：

| 集合 | 查询条件 | 记录数 |
|------|----------|-------:|
| `nextwayv2records` | `{"version":"yahagi-1"}` | 4 |
| `battlerecords` | `{"data.version":"yahagi-1"}` | 4 |

该基线证明当前 HTTP 上报与 MongoDB 入库链路可用。后续修复主要针对本地刷新行为、事件队列恢复和状态可观测性。
