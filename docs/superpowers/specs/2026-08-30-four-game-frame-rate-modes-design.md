# 游戏四档帧率模式设计

## 背景

Yahagi 1.0.5 将游戏帧率模式收敛为「自动」和「低耗」两档，并移除了
1.0.4 中使用裸 `RAF` 的未限速高刷模式。与此同时，应用窗口已经与游戏帧率解耦，
Flutter UI 会请求当前屏幕支持的最高刷新率，游戏内部则继续由 CreateJS Ticker
单独控制。

用户希望恢复游戏高刷，并增加不会自动降至 30 FPS 的固定 60 FPS 模式。新设计将
游戏帧率整理为「自动／60 帧／30 帧／高刷」四档。自动档保留现有保护策略，三个
手动档始终服从用户选择，不由 Yahagi 根据省电、温度、性能采样或生命周期主动切换。

## 目标

- 提供「自动／60 帧／30 帧／高刷」四档游戏帧率设置。
- 自动档保留当前 60 FPS 与 30 FPS 之间的智能切换。
- 60 帧档始终请求 60 FPS，不接受 Yahagi 的自动降档。
- 30 帧档始终请求 30 FPS。
- 高刷档使用裸 `RAF`，持续跟随 WebView 与屏幕实际可用刷新率。
- 高刷通过现有运行时 Bridge 生效，不拦截或修改舰 C 的 `main.js`。
- 每次从其他档位切换到高刷前，显示风险确认弹窗。

## 非目标

- 不拆分舰 C 的游戏逻辑 tick 与画面渲染 tick。
- 不保证设备一定达到 90 FPS、120 FPS 或更高帧率。
- 不绕过 Android 的温控、厂商显示策略或后台 WebView 节流。
- 不重新引入 `main.js` 下载、正则替换或响应拦截。
- 不改变 Flutter UI 已有的最高刷新率请求策略。
- 不重新设计设置页的其他区域。

## 用户可见行为

设置页显示以下四个选项：

| 模式 | 行为 | Yahagi 自动降档 |
| --- | --- | --- |
| 自动 | 正常以 60 FPS 运行；性能持续不稳定、系统省电或设备发热时可降至 30 FPS | 是 |
| 60 帧 | 始终请求 60 FPS | 否 |
| 30 帧 | 始终请求 30 FPS | 否 |
| 高刷 | 解除 60 FPS 限制，使用裸 `RAF` 跟随实际刷新率 | 否 |

这里的「始终」表示 Yahagi 不会主动改变已选手动档。Android、WebView 或设备固件仍
拥有最终调度权，因此系统可能限制实际刷新率，后台页面也可能被 Chromium 暂停或
节流。

建议使用以下简体中文说明：

- **自动：** 正常以 60 FPS 运行，设备状态不佳时自动降至 30 FPS。
- **60 帧：** 始终以 60 FPS 运行，不自动降档。
- **30 帧：** 始终以 30 FPS 运行，降低耗电和发热。
- **高刷：** 解除 60 FPS 限制，跟随屏幕刷新率运行，耗电和发热可能增加。

## 高刷风险确认

每次用户从自动、60 帧或 30 帧切换到高刷时，先显示确认弹窗。弹窗出现时不得提前
保存设置或向游戏发送高刷目标。

简体中文文案固定为：

> **开启高刷模式？**
>
> 高刷会修改游戏运行帧率，可能增加耗电、发热或引发动画异常，并存在未知的账号风险。请自行承担后果。

操作按钮：

- `取消`：关闭弹窗，保留原档位。
- `了解风险并开启`：保存高刷档并立即应用。

已经保存为高刷的用户重新启动应用时直接恢复高刷，不重复弹窗。用户先切换到其他
档位、之后再次选择高刷时，重新显示弹窗。

## 方案比较

### 方案 A：恢复加载期 `main.js` 补丁

在 WebView 加载 `kcs2/js/main.js` 时拦截响应，通过正则把 CreateJS Ticker 的
初始化模式替换为 `RAF`。GotoBrowser 与 Yahagi 1.0.4 使用过这一方案。

该方案能从 Ticker 初始化开始启用高刷，但依赖官方压缩脚本的结构，还会重新引入
网络请求、请求头、资源缓存和 Gadget Bypass 之间的耦合。舰 C 更新后，补丁可能
静默失效或匹配错误，因此不采用。

### 方案 B：通过现有运行时 Bridge 切换

扩展 `YahagiFrameRate` Bridge，使其接受高刷目标，并在 CreateJS Ticker 可用后将
`timingMode` 设置为裸 `RAF`。Bridge 已在文档开始阶段注入，并会定期重新应用目标，
因此不依赖 Ticker 出现的准确时间。

该方案不修改官方资源，可以即时切换，也能在游戏重新设置 Ticker 后恢复用户选择。
这是本次采用的方案。

### 方案 C：分离 60 Hz 逻辑与高刷渲染

保持游戏逻辑每秒更新 60 次，仅让 Canvas 渲染跟随高刷新率。该方案理论风险最低，
但舰 C 将逻辑、Tween、场景更新和渲染混合在 CreateJS Ticker 监听链中。拆分它们
需要识别并改写官方压缩代码，比方案 A 更脆弱，因此不采用。

## 架构设计

### 设置模型

`GameFrameRateMode` 增加两个手动模式，最终包含：

| 模式 | wire name | 初始运行目标 |
| --- | --- | --- |
| `automatic` | `auto` | `fps60` |
| `stable60` | `stable60` | `fps60` |
| `stable30` | `stable30` | `fps30` |
| `highRefresh` | `highRefresh` | `highRefresh` |

设置控制器继续串行保存和应用模式，避免用户快速点击造成旧操作覆盖新操作。普通档位
可以直接保存；高刷必须由界面完成风险确认后才能调用 `setMode`。

### 运行目标

`GameFrameRateTarget` 增加 `highRefresh`：

- `fps30`：设置 `ticker.framerate = 30`，并使用 `ticker.TIMEOUT`。
- `fps60`：设置 `ticker.framerate = 60`，优先使用 `ticker.RAF_SYNCHED`，不可用时
  回退 `ticker.TIMEOUT`。
- `highRefresh`：设置 `ticker.timingMode = ticker.RAF`，不使用 60 FPS 限制。

Bridge 只接受上述三个明确目标。未知目标、Ticker 不存在或 Bridge 不可用时，不执行
高刷修改，并沿用现有不可用提示与安全降级行为。

Bridge 的定期检查继续重新应用当前目标。高刷状态下，如果游戏代码把 Ticker 改回
其他模式，下一次检查会再次设置为裸 `RAF`。

### 模式策略

自动档沿用现有运行策略：

- 前台正常请求 `fps60`。
- 连续性能窗口不稳定时锁定为 `fps30`。
- Android 省电模式开启或热状态达到现有阈值时请求 `fps30`。
- 相关约束解除后，未被性能策略锁定的自动档恢复 `fps60`。

手动档不进入自动策略：

- 60 帧始终请求 `fps60`。
- 30 帧始终请求 `fps30`。
- 高刷始终请求 `highRefresh`。
- 省电、温度、性能样本和应用生命周期变化均不得把手动档改成其他目标。

应用退到后台后，Android WebView 或 Chromium 仍可自行暂停或节流 RAF；Yahagi 不
尝试绕过系统，也不把这种系统行为记录为用户档位变化。回到前台后，Bridge 重新应用
当前手动目标。

### 刷新率边界

Activity 继续请求当前屏幕支持的最高刷新率，不再由游戏帧率设置修改。因而：

- 自动、60 帧和 30 帧只限制 CreateJS Ticker，不降低 Flutter UI 刷新率。
- 高刷的裸 `RAF` 跟随 WebView 获得的实际垂直同步节奏。
- 60 Hz 屏幕上选择高刷不会产生超过 60 FPS 的实际收益。
- Android 因温控或厂商策略降低屏幕刷新率时，高刷会自然跟随较低的实际刷新率；
  这不是 Yahagi 自动降档。

## 配置迁移

- 当前 `auto` 保持为自动。
- 当前 `stable30` 保持为 30 帧。
- 新增 `stable60` 与 `highRefresh` 后直接按各自语义加载。
- 历史 `prefer60`、`followDisplay` 和旧布尔 `game.unlockFrameRate=true` 继续迁移为
  自动，不静默恢复高刷，避免用户绕过风险确认。
- `max60` 继续迁移为自动，`off` 继续迁移为 30 帧。
- 未知 wire name 回退为自动。

## 错误处理

- 高刷确认弹窗取消后，不保存、不通知 Bridge，也不短暂切换界面选中态。
- 保存模式失败时保留原档位，并沿用现有设置错误处理。
- Bridge 不支持或配置失败时标记帧率功能不可用，不尝试恢复 `main.js` 补丁。
- Ticker 尚未创建时，Bridge 保留目标并等待下一次定期检查。
- `ticker.RAF` 不存在时，高刷应用失败并保持页面原有运行方式，不回退到未声明的
  其他高刷实现。

## 本地化与无障碍

- 简体中文、繁体中文和日文资源均增加 60 帧、高刷及风险弹窗文案。
- 四档标签保持简短，详细行为放在选项下方说明中。
- 弹窗标题、正文和两个操作按钮必须提供可读语义，支持屏幕阅读器。
- 确认按钮使用明确的「了解风险并开启」，不使用含义模糊的「确定」。

## 测试策略

### 设置与迁移

- 四个 wire name 均能正确往返保存和加载。
- 当前自动与 30 帧设置升级后保持不变。
- 历史高刷相关值仍迁移为自动。
- 未知值回退为自动。
- 快速连续切换模式时，最终持久化值与最后一次已确认选择一致。

### 设置界面

- 设置页按「自动／60 帧／30 帧／高刷」显示四档。
- 普通三档点击后直接应用。
- 从任意非高刷档选择高刷时显示指定风险弹窗。
- 点击「取消」保持原档位，且不调用设置控制器。
- 点击「了解风险并开启」只调用一次设置控制器并选中高刷。
- 已保存高刷的应用启动时不弹窗。

### Flutter 运行策略

- 自动档可从 60 FPS 降到 30 FPS。
- 60 帧档在性能不稳定、生命周期变化后仍请求 `fps60`。
- 30 帧档始终请求 `fps30`。
- 高刷档在性能不稳定、生命周期变化后仍请求 `highRefresh`。
- 自动性能采样不得改变三个手动档。

### Android 原生层

- 四个模式均能从 Flutter wire name 正确解析。
- 系统省电和热状态只覆盖自动档。
- 60 帧、30 帧和高刷不被系统约束策略改写。
- Bridge 接受 `fps30`、`fps60` 和 `highRefresh`，拒绝未知目标。
- 高刷脚本包含裸 `ticker.RAF`，且不修改 `ticker.framerate` 为虚构值。
- 生产代码不存在因帧率功能拦截或修改 `main.js` 的路径。

### 真机回归

- 在 60 Hz、90 Hz 和 120 Hz 设备或等效测试环境确认实际行为。
- 检查港口、编成、补给、改修、出击、战斗、结算和弹窗动画。
- 确认高刷切回自动、60 帧或 30 帧后立即恢复相应 Ticker 模式。
- 确认应用恢复前台后重新应用用户选择。
- 记录高刷实测 FPS；系统限制导致未达到屏幕标称刷新率不视为功能失败。

### 回归验证

- 运行相关 Flutter 单元测试和组件测试。
- 运行 Android 单元测试。
- 运行 `flutter analyze`。
- 构建 Debug APK，但不自动安装到用户设备。

## 完成标准

- 设置页提供「自动／60 帧／30 帧／高刷」四档。
- 自动档保留现有智能降档，三个手动档不被 Yahagi 自动切换。
- 高刷仅通过运行时 Bridge 使用裸 `RAF`，不修改 `main.js`。
- 每次从非高刷档切换到高刷前显示已确认的简短风险弹窗。
- 取消弹窗不会改变设置，确认后立即保存并应用高刷。
- 历史高刷值不会绕过弹窗静默恢复。
- 自动化测试、静态分析和 Debug APK 构建通过。
