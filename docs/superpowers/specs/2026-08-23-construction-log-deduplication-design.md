# 建造日志跨会话去重设计

## 问题

航海日志会在 `createship` 时插入建造记录。收取舰娘时，`getship` 应更新这条记录。但当前关联关系主要保存在 `LogbookEventRecorder` 的内存中；应用重启或船坞状态信息不完整后，收取阶段可能无法找到原记录，继而把同一次建造再次插入数据库。

典型表现是同一舰娘、同一配方出现两条记录：一条时间为建造开始时间，另一条时间为收取时间。

## 目标

- 同一次建造只保留一条日志。
- 收取舰娘时更新建造开始记录的舰娘和舰种，不新增第二条。
- 应用重启后仍能关联原记录。
- 对确实由其他设备开始、当前设备只负责收取的建造，仍允许补录一条完整记录。

## 方案比较

### 方案 A：数据库持久化待收取状态（采用）

把 `construction_logs` 中 `ship_id` 为空的记录视为待收取记录。收取时按船坞查找最近的待收取记录，并校验建造类型、配方及合理的时间关系；匹配成功则更新，匹配失败才补录。

优点是跨进程可靠，数据库是唯一事实来源，也不依赖内存是否仍然存在。改动范围集中在建造日志的数据访问和记录逻辑。

### 方案 B：只在收取时记录

不再记录建造开始事件，只在 `getship` 时插入。

实现简单，但会丢失建造中的可见记录、开始时间和当时的秘书舰信息，不采用。

### 方案 C：放宽现有时间匹配

继续依赖内存和船坞快照，只扩大时间容差。

无法解决进程重启或状态缺失，且可能把同一船坞的不同建造错误合并，不采用。

## 数据流

1. 收到 `createship`：插入一条待收取记录，并继续保留现有内存缓存作为快速路径。
2. 收到 `getship`：
   - 优先使用内存中的记录 ID 更新。
   - 内存不存在或记录 ID 无效时，从数据库查询该船坞最近的待收取记录。
   - 校验建造类型、配方和时间后更新原记录。
   - 只有数据库中没有可信候选记录，且当前船坞状态足以证明存在一笔未记录建造时，才新增记录。
3. 重复收到同一个 `getship`：已完成记录不会再次插入。

## 边界与安全规则

- 不按舰娘名称去重；同一舰娘可以被正常建造多次。
- 不更新已经有 `ship_id` 且舰娘不同的历史记录。
- 查询范围限定到同一船坞的最新待收取记录，避免跨船坞误配。
- 当前设备没有开始记录时，保留其他设备建造的补录行为。
- 本次不自动删除历史数据库中已经产生的重复记录，避免误删合法的重复建造。

## 测试

新增回归测试覆盖：

- 建造开始后重新创建 `LogbookEventRecorder`，再收取舰娘，数据库仍只有一条记录。
- 船坞快照缺少可还原的开始时间时，仍更新同船坞的待收取记录。
- 其他设备建造且本地没有待收取记录时，收取会新增一条记录。
- 重复处理同一个收取事件不会新增记录。
- 不会把同一船坞较早的已完成记录当作当前待收取记录。

## 验收标准

- 新增回归测试先在当前代码上失败。
- 修复后建造日志相关测试及完整测试套件通过。
- `createship` 与 `getship` 对同一次建造最终只产生一条数据库记录。
- 不修改与航海日志无关的现有工作区变更。
