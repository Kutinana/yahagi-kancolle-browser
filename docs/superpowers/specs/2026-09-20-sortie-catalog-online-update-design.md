# 海域资料在线更新设计

## 目标

在不发布新版应用的情况下更新常规海域资料。维护者更新 Excel 和海域图片、生成并上传版本化资料包后，用户可在设置页手动检查更新；下载成功的资料立即供海域查询使用。

本功能沿用任务资料更新的核心原则：应用内置版本始终可用，远程资料必须经过完整验证后才能替换当前缓存，任何网络、格式或存储失败都不得破坏已有可用数据。

## 范围

首期更新包包含：

- 海域目录 JSON；
- 海域封面图片；
- 路线图图片；
- 版本、兼容性和完整性元数据。

首期只提供设置页中的手动检查按钮，不在应用启动时自动检查或后台下载。敌舰独立资料库不在本期实现范围内；以后可作为同一发布流水线的独立组件加入，不改变海域目录的更新边界。

## 项目内资料目录

海域原始资料迁入当前开发仓库，不再依赖 `G:\日常AI工作\...` 等项目外绝对路径：

```text
data/sortie/
├─ source/
│  ├─ kcwiki_出击_敌舰配置.xlsx
│  └─ images/
│     ├─ 封面/
│     └─ 路线图/
├─ schema/
│  ├─ catalog.schema.json
│  └─ manifest.schema.json
├─ dist/
└─ manifest.json
```

- `source/` 是人工维护的唯一源数据，Excel 和原始图片纳入 Git；
- `schema/` 保存目录和更新清单的机器可验证格式，纳入 Git；
- `dist/` 是本地发布暂存目录，加入 `.gitignore`，ZIP 不进入 Git 历史；
- `manifest.json` 是用户端读取的固定更新入口，生成后纳入 Git；
- `assets/` 中的目录和图片仍是由同一源数据生成的应用内置保底版本，不手工维护。

生成脚本使用仓库相对路径，并允许测试传入临时目录；不得把维护者机器的绝对路径写入目录、清单或归档。

## GitHub 发布物

当前应用 GitHub 仓库保存固定地址的更新清单，版本化 ZIP 作为 GitHub Release 附件上传：

```text
仓库文件：data/sortie/manifest.json
Release 标签：sortie-data-2026.09.20
Release 附件：sortie-data-2026.09.20.zip
```

ZIP 内部结构固定为：

```text
sortie_map_catalog.json
covers/
└─ 8-1.png
maps/
└─ 8-1.png
```

`manifest.json` 至少包含：

```json
{
  "schemaVersion": 1,
  "dataVersion": "2026.09.20",
  "revision": 2026092001,
  "publishedAt": "2026-09-20T12:00:00Z",
  "minimumAppVersion": "1.0.4",
  "archive": {
    "tag": "sortie-data-2026.09.20",
    "fileName": "sortie-data-2026.09.20.zip",
    "bytes": 1234567,
    "sha256": "64位小写十六进制摘要"
  },
  "counts": {
    "maps": 36,
    "nodes": 300,
    "formations": 1200
  }
}
```

`schemaVersion` 描述文件结构；`dataVersion` 是展示给用户的版本；`revision` 是必须递增的整数，用于可靠比较升级和降级；`minimumAppVersion` 防止旧应用加载无法理解的新格式。应用根据内置的 GitHub 仓库、Release 标签和文件名生成下载地址，远程清单不能指定任意主机或完整 URL。

## 数据模型与资源解析

应用内置目录继续使用 `assets/data/sortie_map_catalog.json` 和 Flutter asset 图片。下载版目录中的图片引用统一为 `covers/<海域ID>.png` 和 `maps/<海域ID>.png`；存储层兼容现有内置 JSON 的 `assets/images/sortie_maps/` 前缀，并将两种写法规范化为同一种逻辑资源引用。

新增海域资料来源抽象，对上层统一提供：

- 已解析的 `SortieMapCatalogData`；
- 资料版本与来源（内置或缓存）；
- 将逻辑封面、路线图路径解析为 `Image.asset` 或 `Image.file` 所需资源的能力。

页面不得自行拼接应用支持目录路径。路径解析和安全检查集中在资料存储层，以便测试、回退和后续更换存储结构。

## 更新检查流程

用户在设置页点击“检查海域资料更新”后：

1. 从当前项目仓库允许的 GitHub Raw 地址下载 `data/sortie/manifest.json`，失败时尝试同文件的 jsDelivr 地址。
2. 验证 HTTPS、主机白名单、清单大小、JSON 结构、版本格式和最低应用版本。
3. 将远程 `revision` 与当前最佳可用版本比较；相同则返回“已是最新版本”，更小则拒绝降级。
4. 根据允许的仓库、Release 标签和附件名下载 ZIP 到应用支持目录下的临时文件，同时限制下载字节数。
5. 比较实际字节数和 SHA-256。
6. 解压到独立暂存目录，并执行完整资料验证。
7. 验证成功后，将暂存目录改名为版本目录，再原子更新当前版本指针。
8. 通知海域资料控制器重新加载，新资料立即生效。
9. 更新失败时删除临时内容，继续使用更新前的缓存；缓存不可用时回退到内置资料。

同一时刻只允许一个更新任务。用户重复点击时复用正在执行的 Future，避免并发下载和交叉覆盖。

## 验证与安全

下载资料在激活前必须满足：

- 清单仅通过 HTTPS 从明确允许的 GitHub Raw/jsDelivr 地址读取，归档仅从当前项目的 GitHub Releases 地址读取；
- 清单、压缩包、解压后总大小、单文件大小和文件数量均有上限；
- ZIP 条目不能是绝对路径、不能包含 `..`、不能是符号链接、不能重名；
- ZIP 只能包含目录 JSON、`covers/` 和 `maps/` 下的允许图片类型；
- SHA-256、归档字节数与清单一致；
- JSON 可完整解析，版本、递增修订号和计数与清单一致；
- 海域 ID 唯一，节点 ID 在海域内唯一，编成与敌舰结构合法；
- 每个海域引用的封面和路线图均存在且可解码；
- 缓存目录不能逃逸出应用支持目录；
- 新版本的地图数量不得低于当前最佳可用版本和应用内置基线，避免误上传空库或残缺库。

SHA-256用于验证归档与发布清单一致，不替代发布源信任；发布源仍由应用内的主机和仓库白名单约束。

## 本地存储与回退

应用支持目录使用版本化目录：

```text
sortie-catalog/
├─ active.json
├─ state.json
├─ 2026.09.20/
│  ├─ sortie_map_catalog.json
│  ├─ covers/
│  └─ maps/
└─ 2026.08.30/
```

`active.json` 只在新版本全部验证完成后原子替换。`state.json` 保存当前版本、来源主机、上次检查时间和结果。至少保留当前缓存和上一份缓存；更旧版本可在成功激活后清理。

应用启动时同时检查内置版本和活动缓存：缓存完整、兼容且版本不低于内置版本时优先使用缓存；否则使用内置版本。损坏的活动指针、缺失文件或异常退出留下的临时目录不得阻止页面打开。

## 页面刷新与选择状态

更新成功后，海域查询页面通过控制器通知重新构建，不要求重启应用。

- 当前海域和节点在新目录中仍存在时保持选择；
- 海域存在但节点被移除时回到该海域 A 点，没有 A 点则选择第一个节点；
- 海域被移除时选择新目录中的第一个海域；
- 原有“上次选择”持久化继续使用海域 ID 和节点 ID，不保存缓存文件路径。

更新过程中页面继续显示当前资料，不显示半成品或空白状态。

## 设置页交互

数据设置页新增“海域资料”区块，展示：

- 当前资料版本；
- 资料来源：应用内置或已下载；
- 上次检查时间；
- “检查海域资料更新”按钮；
- 检查中、已是最新、更新成功、版本不兼容、网络失败、校验失败和存储失败状态。

更新成功提示明确说明新版本已立即生效。网络或校验失败提示用户现有资料仍可继续使用，不自动清除已验证缓存。

## 维护与发布流程

维护者执行：

1. 更新仓库内 `data/sortie/source/` 的 Excel、封面和路线图；
2. 运行现有 `build_sortie_map_assets.py` 生成目录、裁边图片和应用内置保底资料；
3. 运行发布命令，在 `data/sortie/dist/` 生成 ZIP，并更新 `data/sortie/manifest.json` 中的计数、文件大小、SHA-256 和版本；
4. 在本地运行结构、图片和回归测试；
5. 提交并推送源资料、Schema、内置资料和 `manifest.json`；
6. 创建对应标签的 GitHub Release，将 `dist/` 中的版本化 ZIP 上传为附件；
7. 用一次真实更新检查验证 GitHub Raw 清单、备用 CDN 清单和 GitHub Release 附件均可读取。

发布脚本拒绝覆盖同名版本，拒绝缺图、重复海域/节点、无效版本和空资料。生成清单时使用确定性文件顺序，保证同一输入产生一致的归档摘要。上传 GitHub 是显式发布步骤，生成脚本本身不执行 `git push`、创建 Release 或上传附件。

## 测试与验收

自动化测试覆盖：

- 内置资料与缓存资料的优先级；
- 无更新、成功更新、拒绝降级和最低应用版本不兼容；
- 主源失败后切换备用源；
- 超时、HTTP错误、超限下载、摘要不符、ZIP路径穿越、缺图和畸形JSON；
- 写入或激活失败后仍能加载旧缓存；
- 异常退出留下临时文件时的恢复；
- 更新成功后页面立即刷新并保持有效的海域/节点选择；
- 发布脚本生成的清单计数、SHA-256和归档内容；
- 设置页各类状态和重复点击去重。

设备验收至少包括普通模式与 HD 模式，分别检查横屏、竖屏和折叠屏展开布局；更新期间和更新完成后页面均可操作。本功能不要求打包 Debug 作为开发阶段验收步骤。

## 非目标

- 不在启动时自动检查或后台静默更新；
- 不从任意用户输入 URL 加载资料；
- 不直接在手机端读取 Excel；
- 不允许远程资料执行代码或修改海域资料目录之外的文件；
- 不在本期实现增量文件补丁、敌舰百科在线更新或活动海域的特殊更新策略。
